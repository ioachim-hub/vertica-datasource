# Vertica Datasource Security Maintenance and Release Design

## Purpose

This repository is a maintenance fork of `rajsameer/vertica-datasource`.
The original plugin is no longer actively maintained, but this fork is still
used as a third-party Grafana dependency. Its purpose is to preserve existing
plugin behavior while keeping the build toolchains and shipped dependencies
free of known security issues.

The next release will modernize both the Go backend and the deprecated Grafana
frontend toolchain. It will remain an unsigned GitHub release intended for
internal installation, not publication in the Grafana plugin catalog.

## Scope

The work includes:

- upgrading to Go 1.26.5, the current supported security patch release;
- updating the Grafana plugin Go SDK and the resulting transitive Go modules;
- migrating the frontend build away from the unsupported
  `@grafana/toolkit`;
- updating compatible Grafana, TypeScript, lint, test, and build dependencies;
- replacing obsolete GitHub Actions and output syntax;
- consolidating releases around one unsigned, tag-driven workflow;
- generating a versioned plugin ZIP and SHA-256 checksum;
- validating the assembled plugin before publishing it;
- documenting maintenance and release conventions in a root `AGENTS.md`;
- updating the changelog and repository documentation.

The work does not include:

- adding plugin features or changing query behavior;
- changing the plugin ID, executable name, or persisted configuration schema;
- publishing to the Grafana plugin catalog;
- signing the plugin;
- requiring Grafana Cloud credentials;
- redesigning the datasource UI;
- changing the Vertica protocol or database behavior unless required for
  compatibility with a supported dependency.

## Compatibility Contract

The following identifiers and behavior remain stable:

- plugin ID: `rajsameer-vertica-datasource`;
- backend executable: `gpx_vertica-datasource`;
- datasource type, JSON settings, secure JSON settings, query model, and
  response behavior;
- installation as an unsigned plugin, with Grafana configured to allow this
  plugin ID;
- ZIP layout with `rajsameer-vertica-datasource/` as its top-level directory.

The minimum supported Grafana version may only be raised when the modernized
Grafana packages or backend SDK make that necessary. Any increase must be
explicit in `src/plugin.json`, `CHANGELOG.md`, and the release notes.

## Dependency Strategy

### Go backend

Use Go 1.26.5 consistently in `go.mod`, local documentation, and GitHub
Actions. Prefer the current stable Grafana plugin SDK version that supports
Go 1.26 and the existing datasource interfaces. Let `go mod tidy` derive
transitive dependencies instead of hand-editing indirect requirements.

The direct Vertica driver remains `github.com/vertica/vertica-sql-go` unless a
newer compatible release is required for security. Dependency updates must be
followed by compilation, tests, vulnerability scanning, and inspection of the
built binaries' embedded module and Go versions.

### Frontend

Replace `@grafana/toolkit` with the build, lint, type-check, Jest, and packaging
configuration currently generated by Grafana's `create-plugin` tooling. The
migration output is a starting point, not an instruction to accept unrelated
scaffolding. Preserve the existing React components and datasource behavior.

Use one JavaScript package manager and one lockfile as the source of truth.
Because the repository currently uses Yarn in CI and documentation,
standardize on Yarn and remove `package-lock.json` after the new Yarn build is
verified.

Avoid broad UI rewrites during dependency migration. Compatibility edits
should be the smallest honest changes needed for current Grafana APIs and
TypeScript types.

## Continuous Integration

The CI workflow runs for pull requests and pushes to `master`. It must:

1. check out the repository with a maintained action;
2. install the pinned Node and Go versions;
3. install frontend dependencies from the lockfile without mutation;
4. lint, type-check, test, and build the frontend;
5. format-check, vet, test, and build the Go backend;
6. run `govulncheck` against the Go packages;
7. assemble the plugin and run Grafana's plugin validator.

Tool versions should be pinned or derived from checked-in configuration.
Workflows must not install floating `latest` tools during a release.

## Unsigned Release Workflow

One workflow replaces the existing signed and unsigned legacy workflows. It
runs on tags matching `v*` and also supports `workflow_dispatch` for packaging
verification without publishing a release.

Before creating a release, the workflow:

1. validates that the tag version matches the plugin/package version;
2. runs the same frontend and backend checks as CI;
3. builds all supported backend executable targets;
4. assembles the complete `dist` directory;
5. validates the plugin;
6. renames `dist` to `rajsameer-vertica-datasource`;
7. creates `rajsameer-vertica-datasource-<version>.zip`;
8. creates a SHA-256 checksum file;
9. verifies the archive layout and executable permission bits.

For a tag event, the workflow creates a non-draft GitHub release and uploads
the ZIP and checksum. The release notes come from the matching
`CHANGELOG.md` section. A manual run uploads the artifacts to the workflow run
but does not create a GitHub release.

The release must not require `GRAFANA_API_KEY`,
`GRAFANA_ACCESS_POLICY_TOKEN`, or another signing credential.

## Versioning

Use semantic versions with a single canonical `v<major>.<minor>.<patch>` tag.
The next maintenance release is expected to be `v2.0.9`, subject to confirming
that no compatibility change requires a minor version.

Do not reuse the old `1.0.9` and `v2.0.8` dual-tag pattern. Release candidates,
when needed, use SemVer prerelease tags such as `v2.0.9-rc.1` and are marked as
GitHub prereleases.

Version metadata must have one documented source of truth and be propagated to
the frontend/package metadata and generated `plugin.json` during the build.

## AGENTS.md

The root `AGENTS.md` will explain:

- that this is a behavior-preserving security-maintenance fork;
- the upstream origin and internal unsigned-distribution model;
- the plugin's frontend/backend structure;
- required Go, Node, and Yarn versions;
- exact install, lint, type-check, test, build, vulnerability-scan, validation,
  and packaging commands;
- the dependency-update policy;
- compatibility boundaries and prohibited opportunistic feature work;
- the version, changelog, tag, and release process;
- how to inspect built binaries and archive layout;
- that existing user changes must be preserved and commits require explicit
  authorization.

## Error Handling and Safety

Dependency migration failures are resolved at the actual API or build
contract. Type casts, disabled checks, blanket vulnerability exclusions, and
removal of tests are not acceptable substitutes.

If a vulnerability has no upstream fix, record the affected package, call
path, runtime reachability, mitigation, and review date. Do not silently
exclude it.

Release creation is gated on all checks and packaging validation. Existing
local release archives are not used as build inputs and are not overwritten.

## Verification

Completion requires evidence for:

- clean frontend dependency installation;
- frontend lint, type-check, tests, and production build;
- `gofmt` cleanliness, `go vet`, Go tests, and all backend builds;
- `govulncheck` with no untriaged reachable vulnerability;
- Grafana plugin validation;
- ZIP contents, directory name, binary targets, and executable permissions;
- installation and datasource health check in a supported Grafana instance;
- a representative Vertica query returning the same result shape as the
  current plugin.

The final handoff lists exact commands, results, remaining warnings, and the
release tag and asset names.
